# Build the filter, borrow the harnesses

robustidps.ai should not move onto OpenHands or Hermes Agent as its base. It should build the one component neither framework ships: an **external, fail-closed predictive safety filter**. The filter sits as a policy decision point between any agent and its tools and returns allow, deny, modify or ask-a-human for every proposed tool call. Existing harnesses should be adopted only as adapter targets and evaluation testbeds. The open frameworks already provide the place to plug this in. Hermes Agent's `pre_tool_call` hook can block, escalate or modify a call and fails closed. The OpenHands SDK's `SecurityAnalyzerBase` scores every proposed action before it runs. Neither of them predicts consequences, and OpenHands returns a risk level rather than a verdict. The evidence says this gap matters. Step-level guards score only **about 40–53 F1** on realistic trajectory benchmarks. Specialised guards' false-positive rates rise **21–47 points** when the same call is written as shell. The best sabotage monitor reaches **AUC 0.87**. Adaptive attacks got past production blocking classifiers in **79%** of trials. Control theory supplies the missing piece: accept an action only if a safe fallback is still reachable afterwards. Only a few 2025–26 papers (ReGuard, SafeMCP, MENTOR) have carried that idea to LLM agents, and none to SOC response or provenance investigation. That leaves robustidps.ai a defensible research position. SOC actions are typed and their reversibility is known, and provenance graphs supply ground truth. The platform's provenance-triage benchmark study (under review) adds direct evidence. Renaming attacker-chosen artefacts raised missed attacks for two frontier models, and the local safeguards had no measurable effect for a strong model, so a filter must reason about effects rather than names. The recommended plan has four phases: harden fail-closed behaviour and the decision contract now; ship a deterministic policy layer with an MCP gateway and approval gates; build a cue-controlled evaluation harness wired into AgentDojo and Inspect; then research the predictive, recoverability-checking filter that would be the publishable contribution.

*Provenance tags used throughout:* **[V]** means verified during the research sessions from primary pages, abstracts or search snippets of primary pages. arxiv.org and several vendor documentation sites failed DNS resolution, so many [V] items rest on snippets rather than full text. **[U]** means the researcher's prior knowledge (to about June 2026), linked to a canonical page but not re-checked in October 2026; check it before citing in a paper. **[vendor]** means a vendor-reported figure with no independent measurement. arXiv IDs of the form 26xx.xxxxx are 2026 preprints and are unreviewed unless a venue is named.

## Hermes returns verdicts, OpenHands returns risk scores, and the rest sit in between

The two reference frameworks the question names differ less in architecture than in what their pre-execution hook is allowed to *decide*.

**OpenHands** has split into two parts. One is the MIT-licensed **V1 Software Agent SDK**: Python, TypeScript and REST APIs, an Agent Server, and the packages `openhands-sdk`, `openhands-tools`, `openhands-workspace` and `openhands-agent-server`. The other is a self-hosted UI, rebranded "Agent Canvas", which runs on that server. The main repository had **~91.7k stars** when fetched [V] ([GitHub OpenHands](https://github.com/OpenHands/OpenHands); [software-agent-sdk](https://github.com/OpenHands/software-agent-sdk)). Workspaces can be the local machine or ephemeral Docker or Kubernetes containers. The Canvas README itself warns that running without a sandbox gives "full access to your filesystem", and that per-conversation containers isolate execution but not the Canvas service [V] ([GitHub OpenHands](https://github.com/OpenHands/OpenHands)).

The security seam is `SecurityAnalyzerBase.security_risk(action: ActionEvent) -> SecurityRisk`. A confirmation policy (`ConfirmRisky`, `AlwaysConfirm`, `NeverConfirm`) turns HIGH or UNKNOWN risk into a pause for human approval. An analyzer exception defaults to HIGH, so the hook fails closed. Conversation history is **not** passed to the analyzer [V] ([analyzer.py](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/main/openhands-sdk/openhands/sdk/security/analyzer.py)). The security module also ships an ensemble analyzer (worst case wins, fails closed), a GraySwan external analyzer and pattern analyzers. The analyzer can be set per conversation through the Agent Server API [V, partly via a third-party source-code study seen only as a snippet] ([arXiv 2609.00006](https://arxiv.org/pdf/2609.00006); [Gray Swan integration](https://docs.grayswan.ai/cygnal/integrations/openhands-integration)). The default `LLMSecurityAnalyzer` asks the *acting* model to rate its own action through an added schema field [V] ([OpenHands security docs](https://docs.openhands.dev/sdk/arch/security)). A prompt-injected agent can understate that rating, so it must never be the only line of defence.

**Hermes Agent** is a separate MIT-licensed agent runtime from Nous Research, distinct from the Hermes model family. It is a long-running, personal-assistant-style agent with persistent memory, skills it writes for itself after complex tasks, a messaging gateway (Telegram, Slack, Signal, email and others), cron jobs, MCP, and terminal backends for local, Docker, SSH, Modal, Daytona, Vercel Sandbox and Singularity [V] ([GitHub hermes-agent](https://github.com/NousResearch/hermes-agent)). Its plugin hook `pre_tool_call` receives the tool name, arguments and session, turn and call IDs. It can return **block** (the message is returned to the model), **approve** (escalate to a human gate, where denial, timeout or gate error fails closed) or **modify** (the new arguments are shallow-merged over the old). Precedence is block > approve. A hook timeout, an exception or a hook still running from the previous call blocks the tool [V] ([hooks.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/hooks.md)). Shell hooks also accept the Claude-Code-style `{"decision":"modify"}` form, so a filter written for Claude-style hooks can be ported [V] (same source).

The caveats are substantial. The repository shows **~256.6k stars and ~58k commits** in roughly eight months, but third-party star counts across 2026 vary wildly, so treat them as indicative only [V] ([GitHub](https://github.com/NousResearch/hermes-agent); [getcoai](https://getcoai.com/article/hermes-ai/)). Release dates (a February 2026 first release, v0.17.0 in June) come only from secondary sources [U] ([agentic-ai.readthedocs](https://agentic-ai.readthedocs.io/en/latest/AgentPlatforms/hermes-agent/)). For a security product, self-authored skills and persistent memory widen the attack surface for memory and skill poisoning (OWASP ASI06), and fast churn makes embedding the framework risky.

AutoGen has been in maintenance mode since October 2025, with Microsoft Agent Framework as its successor [V] ([techstrong.ai](https://techstrong.ai/features/microsoft-ships-agent-framework-1-0-a-production-ready-foundation-for-multi-agent-ai/)). Tier 1 frameworks (verdict plus modify plus ask) are the Claude Agent SDK, Hermes, LangChain middleware, ADK and PydanticAI. Tier 2 (verdict or approval only) includes OpenAI Agents SDK guardrails, Agent Framework approval, Codex and OpenHands. In tier 3 (mini-SWE-agent, smolagents) you subclass the loop yourself. The Claude Agent SDK is effectively tied to one model provider, which rules it out as the sole base for a multi-LLM platform, though its hook format is worth supporting. **No published head-to-head evaluation of pre-execution hooks across frameworks** (latency, coverage, bypass rate) was found.

Sandboxing is the complement the filter needs. Plain Docker shares the host kernel. gVisor intercepts syscalls in a user-space kernel. Firecracker microVMs give each workload its own kernel. Among hosted options, E2B uses Firecracker and Modal uses gVisor; sources conflict on Daytona [V] ([fly.io comparison](https://fly.io/learn/sprites-vs-e2b-vs-modal-vs-daytona/); [northflank](https://northflank.com/blog/e2b-vs-modal)). No provider publishes p50/p99 start latency, and Firecracker's sub-125 ms cold boot is its own figure [vendor] ([fly.io](https://fly.io/learn/sprites-vs-e2b-vs-modal-vs-daytona/); [SoftwareSeni](https://www.softwareseni.com/firecracker-gvisor-containers-and-webassembly-comparing-isolation-technologies-for-ai-agents/)). The filter reduces how often harmful actions are attempted. The sandbox bounds the damage of whatever gets through.

## Control theory supplies the predictive half that LLM guards skip

The phrase "predictive safety filter" has a precise meaning in control. Wabersich and Zeilinger's **model predictive safety filter** certifies a learned controller's proposed input, or changes it as little as possible, so that a feasible, constraint-satisfying backup trajectory to a terminal safe set still exists over a prediction horizon [U] ([arXiv 1803.08552](https://arxiv.org/abs/1803.08552); [arXiv 1812.05506](https://arxiv.org/abs/1812.05506)). Predictive control barrier functions add a soft-constrained problem with a terminal CBF, so feasibility can be recovered after a violation [V] ([arXiv 2105.10241](https://arxiv.org/abs/2105.10241)). Neural approximations remove the online cost that grows with the horizon, at some loss of permissiveness [V] ([arXiv 2211.15104](https://arxiv.org/abs/2211.15104)). CBF filters solve a minimal-deviation quadratic programme that keeps the safe set forward-invariant [U] ([Ames et al.](https://arxiv.org/abs/1903.11199)). Hamilton–Jacobi reachability computes the maximal safe set and a least-restrictive controller [U] ([Bansal et al.](https://arxiv.org/abs/1709.07523)). Hsu, Hu and Fisac's review unifies these approaches as **monitor + fallback + intervention rule** [U] ([arXiv 2309.05837](https://arxiv.org/abs/2309.05837)). Shielding in safe RL either restricts the action set before the agent chooses (pre-shielding) or overrides unsafe actions afterwards (post-shielding) [U] ([Alshiekh et al.](https://arxiv.org/abs/1708.08611)). Latent-space reachability carries HJ analysis into a generative world model's latent space, which turns the constraint specification into a classification problem [V] ([arXiv 2502.00935](https://arxiv.org/abs/2502.00935)). That last step is the bridge to LLM agents, whose "state" is text and tool outputs.

Few papers have made the explicit transfer to LLMs. **ReGuard** ("From Refusal to Recovery", CMU/Princeton, AAAI IASEAI) argues that output classifiers are brittle and that refusal is often not a safe action. It treats agent safety as a POMDP with a latent safe set and a safety value function learned through safety-critical RL, and *corrects* risky actions instead of blocking them [V, details partly secondary] ([arXiv 2510.13727](https://arxiv.org/abs/2510.13727)). **SafeMCP** uses a world model to predict the next state from the partial trajectory when a tool call arrives, labels that state safe, unsafe or critical, and pairs proactive tool pruning (pre-shielding) with a block on predicted-unsafe transitions. It self-reports a >90% safety rate in power-seeking scenarios [V, snippet] ([arXiv 2606.01991](https://arxiv.org/pdf/2606.01991)). **MENTOR** checks tool calls against formalised requirements. Its token-level variant masks unsafe calls during decoding, which is RL shielding applied at generation time [V, snippet] ([arXiv 2610.17039](https://arxiv.org/html/2610.17039v1)). CBF-LLM applies a barrier filter to token generation [U] ([arXiv 2408.15625](https://arxiv.org/abs/2408.15625)). A Barrier Lyapunov follow-up argues that CBFs let outputs drift arbitrarily close to the boundary and enforces a clearance margin instead [V] ([arXiv 2610.17929](https://arxiv.org/html/2610.17929)). "What Can Be Enforced?" sets out a theory of which guarantees can be established before an irreversible step [V existence, content partial] ([arXiv 2607.22868](https://arxiv.org/pdf/2607.22868)). A 2026 survey notes that **blocking individual unsafe actions does not guarantee safe task completion** [V] ([arXiv 2608.14590](https://arxiv.org/pdf/2608.14590)), which is exactly the recoverability point control theory makes.

For defenders the lineage gives a concrete design vocabulary. The **safe set** is the set of states from which the investigation or response can still finish without irreversible harm: evidence intact, business-critical services up, no data sent outside scope. The **dynamics model** is a tool emulator or world model; ToolEmu's LM-emulated sandbox is the offline precedent, and 68.8% of the failures it flagged were judged valid in the real world [U] ([arXiv 2309.15817](https://arxiv.org/abs/2309.15817)). The **backup policy** is escalate to a human, a read-only alternative, or the reversible version of a containment step. The **filter** accepts a call only if a backup remains feasible afterwards.

Conformal prediction adds the calibrated "ask for help" rule. SafePath guarantees, with a user-set probability, that a safe option is in the set and hands control to a human when uncertainty is high, reporting up to 70% fewer collisions [V] ([arXiv 2505.09427](https://arxiv.org/html/2505.09427v1)). KnowNo is the canonical robots-that-ask-for-help planner [U] ([arXiv 2307.01928](https://arxiv.org/abs/2307.01928)). Almost all such work is in robotics. **No calibrated execute-vs-escalate method for general tool-using agents was found**, and no paper computes an explicit reachability value or CBF over a latent state on a real tool-calling benchmark (a negative result from a limited search).

## Action guards remain far weaker than their moderation scores suggest

Guards for agent actions fall into five families, and their headline numbers come from different setups.

The first family is general **content-moderation guards**: Llama Guard, ShieldGemma, WildGuard, Granite Guardian, Qwen3Guard. They score roughly **70–86 F1** on English prompt classification, and the averages shift by several points between the Qwen3Guard report and an independent table, a sign of evaluation sensitivity [V] ([arXiv 2510.14276](https://arxiv.org/pdf/2510.14276); [arXiv 2510.19169](https://arxiv.org/pdf/2510.19169)). No head-to-head tool-call-risk comparison across them exists.

The second family is **injection detectors**. Meta's LlamaFirewall pairs PromptGuard 2 with AlignmentCheck, a chain-of-thought auditor that checks whether actions still serve the user's goal. On AgentDojo it cut attack success from **17.63% to 1.75%**, while utility fell from **47.7% to 42.7%** [V] ([arXiv 2505.03574](https://arxiv.org/abs/2505.03574)).

The third family is **trajectory-aware judges** that rule on the next action before it runs. ShieldAgent reports a 4.8% FPR and 90.1% recall of violated rules [V] ([arXiv 2503.22738](https://arxiv.org/html/2503.22738v1)), and AgentDoG reports 92.7% F1 on R-Judge [V] ([arXiv 2605.29801](https://arxiv.org/pdf/2605.29801)). The sobering number comes from ToolSafe's step-level benchmark, where the purpose-built pre-execution guardian Safiron reaches only **45.9, 39.8 and 52.8 F1** on the AgentHarm, ASB and AgentDojo trajectory splits [V] ([ToolSafe, ACL Findings 2026](https://aclanthology.org/2026.findings-acl.1850.pdf)). Judging whether an action is risky is far harder, and much less saturated, than moderating text.

The fourth family is **deterministic policy enforcement**, which enforces a specification rather than predicting harm. AgentSpec's runtime DSL prevents unsafe executions in over 90% of code-agent cases with millisecond overhead [V] ([arXiv 2503.18666](https://arxiv.org/abs/2503.18666v1)). Progent's least-privilege policies cut AgentDojo attack success from 41.2% to 2.2%; another version reports 39.9% to 1.0% [V, conflict across versions] ([arXiv 2504.11703](https://arxiv.org/html/2504.11703)). SOCpilot's deterministic verifier removed **466 non-compliant, approval-gated actions across 200 real incidents without lowering task recall**, and found that identical inline policy text moved two providers in opposite directions [V] ([arXiv 2605.05501](https://arxiv.org/html/2605.05501v1)). That result argues for enforcing policy outside the model rather than in the prompt.

The fifth family is **architectural isolation**. CaMeL separates a privileged planner from a quarantined parser and tracks capabilities; it solves 77% of AgentDojo tasks with provable security under its threat model, against 84% undefended [V, via secondary snippet] ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). MELON re-runs the trajectory with the user prompt masked and blocks actions that do not depend on it [V] ([arXiv 2502.05174](https://arxiv.org/pdf/2502.05174)). An independent evaluation found Task Shield had a **75% FPR** on AgentDojo's workspace suite even though its utility looked unaffected [V] ([arXiv 2511.15203](https://arxiv.org/html/2511.15203)), a reminder that benchmarks which do not measure false positives hide them.

The AI-control literature treats the agent itself as possibly adversarial, and its monitor numbers are the most sobering. In SHADE-Arena the best monitor reached **AUC 0.87**, which the authors judged "likely prohibitively low" for practice. Human annotators reached 0.65 on a subset [V] ([arXiv 2506.15740](https://arxiv.org/abs/2506.15740)). Ctrl-Z's resampling protocols cut multi-step attack success from 58% to 7% at a 5% benign cost [U for exact figures] ([arXiv 2504.10374](https://arxiv.org/abs/2504.10374)). A 2026 follow-up found that auditing on the *maximum* suspicion across resamples works better than the minimum [V] ([arXiv 2605.26047](https://arxiv.org/html/2605.26047v1)). CUAHarm found that LM monitors catch misuse by computer-use agents far less reliably than chatbot misuse [V] ([arXiv 2508.00935](https://arxiv.org/abs/2508.00935)).

Each robustness finding carries a direct implication for defenders, and the implications matter more than the mechanisms. On **surface form**, ToolRosetta re-rendered identical calls as Python or shell: four of five specialised agent guards shifted sharply, with **FPR up 21–47 points** on AgentDojo, and parsing calls back to a canonical form before guarding removed the effect [V] ([arXiv 2610.24055](https://arxiv.org/abs/2610.24055)). The lesson is to canonicalise before judging. On **language**, LinguaGuardBench translated only the user instruction across 1,220 labelled steps and 19 guards; smaller guards' verdicts flipped measurably and one guard's block rate moved from 12% to 92%, while frontier guards stayed stable [V via mirrors] ([NeurIPS 2026 listing](https://neurips.cc/virtual/2026/168173)). Small guards therefore need language-invariance tests. On **false-positive denial of service**, short adversarial strings made Llama Guard 3 block over 97% of requests [V] ([arXiv 2410.02916](https://arxiv.org/html/2410.02916v3)), and reasoning guardrails can be pushed into 13–63× token amplification [V, partly secondary] ([arXiv 2606.14517](https://arxiv.org/pdf/2606.14517)). A filter's false positives and latency are themselves an attack surface, so fail-closed designs need budgets and circuit breakers.

On **adaptive attacks**, attacks on trusted monitors consistently evaded diverse monitors, and resampling turned into a best-of-n advantage for the attacker [V] ([arXiv 2510.09462](https://arxiv.org/abs/2510.09462)). Search-based adaptive attacks raised static attack success of about 1% to over 95% against two prompt-injection defences [V] ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023)). Red-teaming of Claude Code Auto Mode and an approximation of a Codex guardian reached arbitrary command execution in **79%** of trials, and multi-context attacks at acceptable cost remain unsolved [V] ([arXiv 2609.19587](https://arxiv.org/pdf/2609.19587)). The Cloud Security Alliance accordingly treats such classifiers as productivity controls, not replacements for sandboxing and egress control ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-opus5-automode-injection-20260/)).

The pattern across these failures points to a design principle. **Monitors that read agent-authored text inherit its attack surface.** That includes chain-of-thought, rationales and free-form arguments; ToolRosetta found that removing the agent's rationale changed most guards that take it as input. A filter that reasons over canonicalised action semantics and predicted state is structurally less exposed.

## No benchmark yet labels SOC response actions for a filter to judge

The benchmark ecosystem is rich for prompt injection and misuse but thin exactly where robustidps.ai operates.

|---|---|---|---|

| Inspect approval policies (AgentHarm, Cybench, others) | Misuse with benign twins; capability [U] ([Inspect approval](https://inspect.aisi.org.uk/approval.html); [AgentHarm](https://arxiv.org/abs/2410.09024)) | Yes: custom approver can accept/modify/reject/escalate per call | Over-refusal measurement; cross-suite generality |
| TS-Bench, R-Judge, ASSEBench, ShieldAgent-Bench | Labelled steps or trajectories for judges [V]/[U] ([ToolSafe](https://arxiv.org/abs/2601.10156); [ASSEBench](https://arxiv.org/abs/2506.00641)) | Offline only | Calibration sanity checks, not headline results |
| CUAHarm, SHADE-Arena | Host misuse; covert sabotage; monitors scored separately [V] ([CUAHarm](https://arxiv.org/abs/2508.00935); [SHADE](https://arxiv.org/abs/2506.15740)) | Trajectories / transcripts | Template for scoring the monitor apart from the agent |
| MCPTox, MSB, MCP-SafetyBench, MCPSecBench | Tool poisoning and protocol attacks on MCP [V] ([MCPTox](https://arxiv.org/abs/2508.14925); [MCP-SafetyBench](https://arxiv.org/abs/2512.15163)) | Partly; MCPSecBench tests whole products, so model and product are confounded ([COPEX critique](https://arxiv.org/html/2610.04378)) | MCP/agent-scanning use case |
| ExCyTIn-Bench, CyberSOCEval, AuditBench, DiagChain | SOC investigation over logs, malware/CTI reasoning, audit logs, attack-chain reconstruction [V] ([ExCyTIn](https://arxiv.org/pdf/2507.14201); [CyberSOCEval](https://arxiv.org/abs/2509.20166v1); [AuditBench](https://arxiv.org/pdf/2606.10281); [DiagChain](https://arxiv.org/html/2608.03591v1)) | No documented hook (ExCyTIn's SQL tool could be wrapped) | Capability baselines; none labels response actions as safe or unsafe |

Three findings shape the protocol. First, **MCPTox's best refusal rate was under 3%** [V] ([arXiv 2508.14925](https://arxiv.org/abs/2508.14925)), so the model's own refusals give almost no protection against poisoned tool metadata, and an external layer is the relevant control. Second, AuditBench found LLMs treat audit logs as overly suspicious [V, secondary summary] ([arXiv 2606.10281](https://arxiv.org/pdf/2606.10281)), so a SOC filter's false-positive rate on benign containment must be reported alongside its catch rate. Third, NIST/CAISI's hijacking evaluation found that existing attacks reached **11%** success while novel agent-specific attacks reached **81%**, and that multi-attempt testing gives more realistic estimates [V] ([NIST technical blog](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations)). Adaptive, multi-trial evaluation is no longer optional.

The most important gap is **lexical mimicry**. Work on log-borne prompt injection exists. Poisoning the Watchtower embeds content in attacker-controllable log fields [V] ([arXiv 2605.24421](https://arxiv.org/html/2605.24421)). In LogJack, one open model executed injected content in 86.2% of active-mode trials while a frontier model did so in 0% [V] ([arXiv 2604.15368](https://arxiv.org/pdf/2604.15368)). All of that work uses *instructional* payloads. Classical provenance-IDS mimicry attacks target graph detectors, not LLM filters [U] ([Goyal et al., NDSS 2023](https://www.ndss-symposium.org/ndss-paper/sometimes-you-arent-what-you-do-mimicry-attacks-against-provenance-graph-host-intrusion-detection-systems/)). A3S-Bench's semantic evasion targets the agent's own behaviour, not a separate filter's verdict [V] ([arXiv 2605.22321](https://arxiv.org/html/2605.22321v1)). **No benchmark was found that measures whether a filter or monitor on agent actions is fooled by non-instructional, attacker-chosen names in telemetry.** The real-world basis is MITRE ATT&CK T1036 Masquerading [U] ([MITRE T1036](https://attack.mitre.org/techniques/T1036/)). The platform's provenance-triage benchmark study (under review) supplies the first evidence from this gap: renaming attacker-chosen artefacts raised missed attacks for two frontier models, and the local safeguards had no measurable effect for a strong model. Any novelty claim should be phrased narrowly, as *filter and monitor robustness to non-instructional lexical cues in telemetry*. Before it is made, the threat-model sections of ProvAgent, DiagChain, AuditBench and the log-injection papers need checking, because only their abstracts could be read.

The evaluation protocol for robustidps.ai's filter follows from all of this. Detection should be scored at both the action and the episode level, as **TPR at fixed FPR of 1% and 5% plus AUROC**, with the monitor scored separately from the agent as CUAHarm and SHADE-Arena do. Utility should be reported with the filter on and off, both without attack and under attack, together with the over-blocking rate on benign SOC actions and the **human-approval rate**, since every "ask" costs analyst time. Attack success should be reported under static benchmark attacks and under an adaptive attacker who knows the filter and has a multi-attempt budget, reported as pass@k, following NIST and "The Attacker Moves Second". Robustness should be tested across cue-controlled variants of the same scenarios (original, names neutralised, benign-sounding names) with the **renaming delta as the headline metric**, plus benign look-alikes to expose over-suspicion, ToolRosetta-style surface-form re-rendering, and LinguaGuardBench-style instruction translation. Cost should be reported as p50/p95 added latency and tokens or dollars per action, including the worst case under induced reasoning blow-up.

Baselines should include PromptGuard 2 with AlignmentCheck, a strong open guard (Qwen3Guard or Granite Guardian), an LLM judge in the AgentAuditor style, a rule/allowlist verifier in the SOCpilot or Progent style, and OpenHands' own analyzers. Each filter component should be ablated. The agent's existing ablation switches in `bluesec/robust/investigation.py` (`use_cache`, `use_validation`, `use_grounding`, `use_budget`) are the right precedent. Small task sets need per-task paired results with exact binomial or bootstrap intervals, and per-row verdicts should be released, as ToolRosetta does. To make results directly comparable with prior work, the filter should be packaged as an AgentDojo pipeline element and an Inspect approver.

## Security agents converge on "the LLM proposes, a deterministic system disposes"

Offensive tooling is now a crowded open-source category. Strix (Apache-2.0), Shannon (AGPL-3.0 plus commercial), PentAGI (MIT), HexStrike-AI (an MCP server bundling security tools) and CAI (reportedly archived; licence possibly non-OSI, unverified) share one design: a planner/executor loop, Docker-sandboxed tooling increasingly exposed over MCP, and deterministic validation of findings [V via search summaries] ([Strobes](https://strobes.co/blog/open-source-agentic-pentesting-tools/); [Ostorlab](https://blog.ostorlab.co/9-open-source-ai-pentest-tools-2026.html)). The safety controls these tools lack are the relevant part for robustidps.ai. Public documentation describes target allow-lists, Docker isolation and human review, but **no declarative rules-of-engagement engine** enforcing targets, network ranges, time windows and permitted technique classes outside the model. They also default to Docker, the weakest isolation tier [V] ([Strobes](https://strobes.co/blog/open-source-agentic-pentesting-tools/)). Benchmarks of these tools are vendor-run or confounded by model choice [V] ([Escape](https://escape.tech/blog/benchmarking-agentic-ai-pentesting-tools/)).

The commercial frontier shows where reliability actually comes from. XBOW reached #1 on HackerOne's US leaderboard in June 2025 with human review before submission, and credited its low false-positive rate to **deterministic validators**, not LLM judgement [V via search summaries] ([TechRepublic](https://www.techrepublic.com/article/news-ai-xbow-tops-hackerone-us-leaderboad/); [Dark Reading](https://www.darkreading.com/vulnerabilities-threats/ai-based-pen-tester-top-bug-hunter-hackerone)). DARPA AIxCC finalists paired fuzzing oracles with LLM components [V] ([DARPA](https://www.darpa.mil/news/2025/aixcc-results)). Incalmo's design, in which the model issues high-level intents and a separate action layer translates them into tool calls, puts a natural enforcement point at the translation layer [U] ([arXiv 2501.16466](https://arxiv.org/abs/2501.16466)). Dual-use pressure is real: Check Point reported threat actors discussing HexStrike-AI [U] ([Check Point blog](https://blog.checkpoint.com/)). That strengthens the case for scope enforcement in any authorised-testing feature robustidps.ai offers.

Defensive "agentic SOC" products have shipped from every major platform, with large but unverified speed-ups. Google claims a 30-minute triage cut to about 60 seconds [vendor] ([TechInformed](https://techinformed.com/googles-soc-agent-cuts-alert-review-from-30-minutes-to-60-seconds/)), and Microsoft claims 6.5× more malicious alerts identified by its Phishing Triage Agent [vendor] ([Redmond Mag](https://redmondmag.com/articles/2025/08/06/microsoft-rolls-out-phishing-triage-agent-in-security-copilot-public-preview.aspx)). One analyst counts **about 220 AI-SOC products and "no scoreboard"** ([Simonnet](https://cyrilsimonnet.substack.com/p/220-ai-socs-sixteen-prices-and-no)). Academic provenance agents follow the same verifier pattern. ProvSEEK issues bounded provenance queries [V] ([arXiv 2508.21323](https://arxiv.org/pdf/2508.21323)). HunterAgent lets the LLM only propose hypotheses that symbolic checks then verify, which holds up under anti-forensics [V] ([arXiv 2605.29269](https://arxiv.org/abs/2605.29269)). An October 2026 triage-failure study notes that provenance methods need causal graphs that standard telemetry usually lacks [V, abstract only] ([arXiv 2610.10608](https://arxiv.org/html/2610.10608v1)). Practitioner tiering is consistent across vendors: read-only queries run autonomously, reversible containment may be pre-authorised, and disabling accounts or isolating servers needs approval [vendor] ([UnderDefense](https://underdefense.com/blog/human-in-the-loop-soc-design/); [Simbian](https://simbian.ai/blog/ai-agent-guardrails-soc)).

MCP is now both the default tool layer and a major attack surface. The incidents include mcp-remote CVE-2025-6514 (CVSS 9.6) [V] ([GHSA-6xpm-ggf7-wc3p](https://github.com/advisories/GHSA-6xpm-ggf7-wc3p)); the postmark-mcp server, which turned malicious after 15 benign versions; and a GitHub MCP data leak traced to over-broad token scope combined with untrusted content [V] ([AuthZed timeline](https://authzed.com/blog/timeline-mcp-breaches)). A 2026 paper found an **approval-view fidelity gap**: the text a user approves can differ from what the model receives [V] ([arXiv 2607.05744](https://arxiv.org/pdf/2607.05744)). The fix is to render approvals from a canonicalised view. Defences come in two classes. Pre-install scanners include Snyk Agent Scan (formerly Invariant mcp-scan, v0.5.12 in June 2026) and Cisco's open-source MCP Scanner. Runtime gateways include Docker MCP Gateway, Lasso, Cloudflare and Pomerium. Practitioners recommend description hash-pinning plus a runtime gateway, because scanners cannot stop malicious tool *results* [V] ([Maxim](https://www.getmaxim.ai/articles/best-mcp-security-tools-in-2026/); [Practical DevSecOps](https://www.practical-devsecops.com/top-mcp-security-tools/)).

For traces, OpenTelemetry GenAI conventions define `invoke_agent` and `execute_tool` spans. They are still in **Development** status, with no stability timeline, and do not capture tool arguments by default [V] ([OTel spec](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans); [Greptime](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)). Any integration therefore needs a version pin and an adapter layer.

The standards give the filter's controls a ready-made taxonomy. The **OWASP Top 10 for Agentic Applications 2026** (ASI01–ASI10, published December 2025) [V] ([Giskard](https://www.giskard.ai/knowledge/owasp-top-10-for-agentic-application-2026); [Modulos](https://docs.modulos.ai/frameworks/owasp-top-10-agentic)) maps cleanly onto the architecture's components:

| OWASP ASI risk | robustidps.ai control |
|---|---|
| ASI01 Agent Goal Hijack | Taint tracking of arguments derived from untrusted telemetry; goal-alignment signal in the filter |
| ASI02 Tool Misuse | Policy decision point on every call; tiered action table |
| ASI03 Identity & Privilege Abuse | Credential broker; per-tool, per-tenant short-lived tokens kept out of model context |
| ASI04 Agentic Supply Chain | Pinned MCP catalogue, description hashing, scanner in CI |
| ASI05 Unexpected Code Execution | Sandbox tiers (Docker → gVisor → Firecracker) chosen per tool |
| ASI06 Memory & Context Poisoning | No autonomous skill writing; reviewed, signed skills; memory scoped per tenant |
| ASI07 Insecure Inter-Agent Communication | Authenticated, logged agent-to-agent messages through the same decision point |
| ASI08 Cascading Failures | Call budgets, circuit breakers on filter latency, rollback for reversible actions |
| ASI09 Human-Agent Trust Exploitation | Canonicalised approval rendering with blast-radius preview |
| ASI10 Rogue Agents | Asynchronous runtime monitor plus hash-chained agent-action provenance log |

The OWASP LLM Top 10 2025 entry LLM06 "Excessive Agency" [U] ([OWASP](https://genai.owasp.org/llm-top-10/)) and the OWASP MCP Top 10 [V] ([Cycode](https://cycode.com/blog/owasp-mcp-top-10/)) complete the OWASP set. MITRE ATLAS added agent-specific techniques through 2026, but version and technique counts conflict across sources (from 84 to 120 techniques), so check them at atlas.mitre.org before citing [V conflict] ([Vectra](https://vectra.ai/topics/mitre-atlas); [Speakeasy](https://www.speakeasy.com/blog/mitre-atlas-explained)). A CAISI, Gray Swan and UK AISI competition reportedly hijacked **every one of 13 frontier models** at least once [V, via an AI-assisted CSA note] ([NIST CAISI blog](https://www.nist.gov/blogs/caisi-research-blog/insights-ai-agent-security-large-scale-red-teaming-competition)). The EU AI Act Digital Omnibus provisionally defers Annex III high-risk obligations to 2 December 2027, though formal adoption was still pending as of June 2026 [V] ([Gibson Dunn](https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines-and-other-key-changes/)). Security tooling is generally outside Annex III unless it serves as a safety component of critical infrastructure [U; needs legal review]. Near-term compliance pressure will therefore come from procurement checklists rather than regulators. Tagging every control and test with its ASI, LLM, ATLAS and NIST AI RMF identifiers is cheap and valuable.

## Recommended architecture: an external, fail-closed policy decision point

**The build-versus-adopt answer: build the safety layer and adopt the agent loops.** robustidps.ai already has a Python agent with local safeguards, an Agent Studio, and an Agent Security plugin set (scanner, red-team automation for agent specs, runtime monitor, OTel receiver). Its research contribution is the safety layer, not the loop. Adopting OpenHands wholesale would bring in a coding-centric, Docker-heavy harness with ~90k stars' worth of surface area unrelated to provenance graphs. Adopting Hermes would bring in a fast-changing personal-assistant runtime whose self-written skills and memory are liabilities in a SOC. Writing adapters is cheap, because the decision semantics already converge on allow/deny/modify/ask.

```
 user-customised agent (in-house triage agent | OpenHands SDK | Hermes | LangGraph | ...)
        │ proposed tool call
        ▼
 ┌──────────────── Safety filter / policy decision point (robustidps.ai, built) ────────────────┐
 │ L0 canonicalise: parse to typed action; resolve entities to stable IDs; strip rationale    │
 │ L1 deterministic policy: scope/RoE, action tier, allow-lists, argument taint/provenance    │
 │ L2 predictive check: effect model over abstract state → is a safe backup still reachable?  │
 │ L3 learned signals: guard model / LLM judge (worst-case ensemble, never sole authority)    │
 │ L4 calibrated deferral: conformal threshold → ask human with canonical render + blast radius│
 │ → {allow | deny | modify | ask}, fail closed on error, timeout, or repeat of a denied call  │
 └───────────────────────────────────────────────┬───────────────────────────────────────────┘
                                                 ▼
 MCP gateway (pinning, per-tool credentials, result filtering) → sandbox tier → tools
        │ every decision + result
        ▼
 runtime_otel.py spans → runtime_monitor.py (async allow/warn/block analytics) → hash-chained provenance log
```

The **filter contract** follows Hermes and Claude-style hook semantics so that one implementation serves every harness. The input is `{session_id, turn_id, tool_name, args, transcript_ref, actor_role, environment, scope_ref, arg_provenance}`. The output is `{decision: allow|deny|modify|ask, modified_args?, risk: LOW|MED|HIGH|UNKNOWN, score, reason, filter_version, policy_version}`. The adapters are thin. For OpenHands, return `SecurityAnalysis(risk=HIGH, details=...)` under `ConfirmRisky`; this gives deny-by-pause but not modify, and history must be fetched separately because the analyzer does not receive it. For Hermes and Claude-style hooks, return hook JSON. For LangChain, wrap the call as `wrap_tool_call` middleware. For evaluation, package it as an AgentDojo pipeline element and an Inspect approver. Running the filter as a separate service, not a library inside the agent process, keeps a compromised agent from rewriting it, and keeps it consistent with the AI-control assumption that the agent may be adversarial.

Each layer answers a specific weakness found in the evidence. **L0 canonicalisation** is ToolRosetta's demonstrated fix for surface-form brittleness. Its other job is to remove the agent's rationale and replace attacker-chosen names with stable entity IDs and typed attributes such as process lineage, signer, path class and network destination class. That second step is the direct engineering response to the platform's study: a filter that never sees the names cannot be swayed by them. **L1 deterministic policy** is where scope enforcement for authorised testing lives. A declarative rules-of-engagement schema (permitted targets and ranges, time windows, permitted technique classes, intensity limits, data-handling rules) is compiled into policy and enforced outside the model; none of the reviewed offensive tools offers this. For SOC response, the same layer holds the action-tier table, from enrich and annotate through ticket and block indicator to isolate host and disable identity, following SOCpilot's evidence that verifiers outside the model remove non-compliant actions without hurting recall. **L2 prediction** is the research layer, discussed below. **L3 learned guards** contribute signals combined worst-case-wins, as in OpenHands' ensemble, but never act as the sole authority, because adaptive attacks and DoS strings target exactly these components. **L4 deferral** turns uncertainty into a calibrated "ask". It is paired with canonicalised approval rendering to close the approval-view fidelity gap, and with dual approval for actions at isolation tier and above.

Reversibility decides what must be synchronous. Read-only queries and reversible containment can run with only L0–L1 synchronously, with deeper analysis done asynchronously by the runtime monitor and rollback available. Irreversible or out-of-scope-risk actions take the full synchronous path. This keeps latency off the common case and puts it where control theory says it belongs.

**The existing code needs two specific changes.** First, `bluesec/robust/investigation.py` deliberately lets an unchanged repeat of a locally rejected call through. Its docstring says "A locally rejected call is sent anyway the second time the agent makes it unchanged, because the runtime, not this module, is the authority", and the code skips validation and grounding for any call key in `_rejected`. That is a sound **efficiency** choice for schema and grounding hints, whose job is to save tool calls. It is the wrong semantics for a **safety** filter, which must fail closed. A denied call must stay denied when resubmitted unchanged, repeated attempts should count as an escalation signal, and only a human approval, a changed state or a new policy version should unlock it. The filter must therefore sit *outside* the `if key not in self._rejected` branch, and timeouts, exceptions and overlapping invocations must all produce a deny, mirroring Hermes and OpenHands. Cache hits replay results of calls that were already allowed and executed, so they are safe to keep. They should still be logged as decisions, and policy-version changes should be recorded on the trace. Second, `backend/plugins/agent_studio/runtime_monitor.py` currently *ingests* allow/warn/block verdicts produced elsewhere into an in-memory, 100-event rolling window and alerts above a 20% block rate. `runtime_otel.py` maps GenAI spans, with custom decision attributes, into that stream. That makes it an asynchronous analytics layer, not a gate. It should keep that role, fed by the new decision point, while moving to per-tenant persistent storage and adding a filter-decision span type with a pinned semantic-conventions version.

The study's second finding sets a further requirement. The local safeguards had no measurable effect for a strong model, so **efficiency safeguards are not safety evidence**. Every filter layer must earn its place through an ablation on the cue-controlled variants, using the same switch pattern the agent already has.

| Component | Decision | Rationale |
|---|---|---|
| Safety filter / policy decision point, RoE schema, action tiers, canonicaliser | **Build** | The research contribution; no open framework offers predictive or recoverability checks |
| Agent loop for provenance triage | **Keep in-house** | Already instrumented with ablations and traces; domain-specific tools |
| OpenHands SDK | **Adopt as second harness** | Security-native analyzer seam; built-in LLM, GraySwan and pattern analyzers serve as baselines |
| Hermes / Claude-style hooks, LangChain middleware | **Adopt as adapter targets** | Shows the filter generalises across hook APIs; users bring their own agents |
| mini-SWE-agent | **Adopt for ablations** | Minimal, easy to wrap, JSON trajectories |
| AgentDojo, Inspect, AgentHarm | **Adopt for evaluation** | Native defence and approver hooks; comparability |
| PromptGuard 2 / LlamaFirewall, Qwen3Guard, Granite Guardian | **Adopt as L3 signals and baselines** | Open weights; known numbers |
| Docker MCP Gateway or Lasso; Snyk Agent Scan / Cisco MCP Scanner | **Adopt and extend** | Extend with scope-aware credential binding and result filtering |
| gVisor (Modal-class) and Firecracker (E2B-class) sandboxes | **Adopt** | Docker only for read-only triage; microVMs for testing tools and unknown samples |
| Hermes or OpenHands Canvas as platform base; AGPL or non-OSI offensive tools as embedded components | **Avoid** | Attack surface, churn, licence constraints |

Users customise the framework through four controlled surfaces rather than by forking a harness: policy packs (scope/RoE and tier tables as YAML), a pinned tool catalogue, reviewed skills in the AgentSkills format that OpenHands and Hermes both use, and filter plugins written against the stable contract. That gives the openness of OpenHands or Hermes while keeping the safety layer under the platform's control.

## Six research gaps worth a paper

The first and strongest direction is a **model-predictive safety filter for SOC containment**. The state is an abstraction of the environment and the provenance graph: host isolation status, account status, whether evidence is preserved, the attacker's foothold. A learned or LLM effect model predicts each action's consequence, the safe set encodes service availability and evidence integrity, and the backup is escalate or read-only. An action is accepted only if a backup stays feasible over a horizon. This would make ReGuard and SafeMCP concrete in a domain with crisp semantics, and it can be compared directly against step-level guards (TS-Guard, AlignmentCheck) and rule verifiers (SOCpilot-style, Progent, AgentSpec). No predictive or consequence-based filtering over provenance graphs was found in the literature.

The second is **reversibility-aware synchronous/asynchronous splitting**, which answers an open question in AI control: which actions can be monitored after the fact, with rollback, and which need a gate in front of them. It would report latency saved against safety retained. The third is **mimicry-robust filtering**. It would extend the platform's study from triage agents to the filters and monitors that oversee them, and test canonicalisation, entity abstraction and predicted-state filtering as defences against adaptive renaming. No benchmark yet does this, and ToolRosetta explicitly covers only benign re-rendering.

The fourth is **calibrated deferral**. Conformal risk control would bound the miss rate of unsafe containment actions at a chosen escalation budget, the analogue of the auditing budget in AI control; no such method was found for general tool agents. The fifth is a **labelled SOC response-action benchmark**, in which isolate, kill, block and disable actions carry safe/unsafe labels for a filter to judge. No public benchmark of this kind was found, and the market's "no scoreboard" problem makes a neutral harness valuable beyond academia. The sixth is a **cross-framework hook evaluation**, measuring coverage, latency and fail-closed behaviour of the same filter across the OpenHands, Hermes, Claude-style, LangChain and Inspect seams. No such comparison exists.

Two adjacent contributions are engineering rather than science but could still be published. One is a declarative **RoE/scope schema** for authorised testing agents; no source documented a standard. The other is an **agent-action provenance graph** that links input, retrieved artefact, model step, filter decision, approval and tool effect, reusing the platform's provenance expertise for agent forensics. Every claim in this section rests on negative search results from a limited search, so a targeted related-work pass (Invariant/Snyk Guardrails, NeMo Guardrails, Lakera/Check Point, and the full texts of the 2026 log-injection and provenance-agent papers) must precede any novelty claim.

## Conclusion

The question asked how to build an OpenHands- or Hermes-style framework. The evidence says the framework is the easy part and has largely been commoditised, since every serious harness now exposes a pre-execution seam with converging semantics. What is missing everywhere is a decision layer that checks whether a proposed action leaves a safe way back, rather than asking whether the call *looks* dangerous. Today's guards mostly answer the second question, and that is why they break under renaming, re-rendering, translation and adaptive pressure. A SOC is close to the ideal setting for the first question: actions are typed, reversibility is known, policies already exist as playbooks, and provenance graphs supply ground truth.

The platform's own study turns a theoretical argument into a design requirement. If names sway the agent, names must not reach the filter. If local safeguards do not move outcomes for strong models, then efficiency features cannot stand in for safety evidence. Both lead to the same engineering rule: a safety filter must sit outside the agent, see canonical effects rather than attacker-chosen text, and fail closed, including on the second identical attempt.
